# API Reference — Phase 2A backend

> **Generated by reading the route modules** (`app/*/routes.py`, `app/api/system.py`) as of the
> pre-Phase-3 prep. If you change a route, update this file. This is a *reference*, not a contract test —
> the behavioural contract is the pytest suite under `tests/phase2a/`.

All endpoints are served under the `/api` prefix, same-origin, by the Flask app. The desktop UI
(`app/ui.py` + `app/web/`) is the only client. There is **no networked/remote API** — the server binds
`127.0.0.1` on an ephemeral port (`main.py:start_server`).

## Response envelope

Every JSON response uses one of two shapes (`app/api/responses.py`):

```jsonc
// success
{ "ok": true,  "data": <any> }
// failure
{ "ok": false, "error": { "code": "<UPPER_SNAKE>", "message": "<human text>" } }
```

Error handlers for `404 / 405 / 413 / 500` return the same envelope (`app/api/errors.py`), so a client
never has to parse an HTML error page.

## Authentication model

- **Single account.** One username/password per install (`app/auth/account.py`). `auth.json` holds
  exactly `{username, bcrypt_hash, created_at}` — **no key material** (the server master key is a
  process concern, not password-derived; see below). `authenticate()` is a bcrypt-only credential
  check. No multi-user yet — the multi-account `users` table replacing `auth.json` lands in increment
  3.2b-2.
- **Server master key + fail-closed lock (Phase 3 increment 3.2b-1, ADR 0003 pt 2).** The server holds
  one SQLCipher master key for the whole process, unwrapped at **startup** from a bootstrap passphrase
  (`NEXUSLINK_BOOTSTRAP_PASSPHRASE` env or console prompt) into `app.config["DB_KEY"]` — see the README "Server
  bootstrap" note. Until it is set, the server is **LOCKED:** every `/api/*` route returns **`503 LOCKED`**
  **except `/api/health` and `/api/status`** (so a client can observe the locked state). A bad passphrase
  never crashes the server; it starts locked. This server-wide gate (`api.guards.install_lock_gate`) is
  distinct from `@login_required`, which gates a per-session login once the server is unlocked.
- **Session:** a signed Flask cookie (`SESSION_COOKIE_HTTPONLY`, `SameSite=Strict`, per-launch
  `SECRET_KEY`). `session["authenticated"]` gates protected routes; `session["username"]` carries the
  operator identity (see below).
- **Identity is per-session** (Phase 3 increment 3.2a, ADR 0003 pt 1): the unlocked account's username
  lives in the signed session cookie via `app/api/identity.py` (SUPPORT), read through the single
  accessor `api.guards.current_username()`. It is **no longer** in `current_app.config["USERNAME"]`
  (that slot was removed).
- **The DB key stays process-global** (`current_app.config["DB_KEY"]`) — since 3.2b-1 it is set **once
  at server startup** from the bootstrap passphrase and is **not** cleared at logout (the master key is
  process-wide, so locking it would lock the server for every operator). **Login/logout no longer
  unlock/lock the DB** — `login` only establishes the session identity + `authenticated` flag, and
  `logout` only clears the session. The fail-closed guarantee is therefore "no session identity is
  granted" (an unauditable login/setup grants no session behind its 500), not "DB_KEY is cleared." See
  `docs/phase3-surface.md` for the full de-globalization inventory and what still moves in 3.2b-2.
- **`@login_required`** (`app/api/guards.py`) returns `401 UNAUTHENTICATED` if not logged in, and
  `415 BAD_CONTENT_TYPE` if a state-changing request has a body that isn't JSON or multipart.

## Endpoints

### System (public)

| Method | Path | Body | Success | Notes |
|---|---|---|---|---|
| GET | `/api/health` | — | `200 {"status":"ok"}` | Liveness probe (used by `wait_until_ready`). Reachable while LOCKED. |
| GET | `/api/status` | — | `200 {"locked":bool,"account_exists":bool,"authenticated":bool}` | Drives locked/first-run/login UI. `locked` = master key not yet unwrapped. Reachable while LOCKED. |

Both System routes stay reachable while the server is LOCKED; every other `/api/*` route returns
`503 LOCKED` until the master key is unwrapped (see Authentication model).

### Auth

| Method | Path | Auth | Body | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/setup` | public | `{username, password}` | `201 {"username"}` | `400 BAD_REQUEST` (missing/blank, or password >72 bytes), `409 ACCOUNT_EXISTS` |
| POST | `/api/login` | public | `{username, password}` | `200 {"username"}` | `400 BAD_REQUEST` (missing/blank), `401 UNAUTHENTICATED` (also appends to `login_failures.log`) |
| POST | `/api/logout` | required | — | `200 {}` | `401` |
| POST | `/api/change-password` | required | `{old_password, new_password}` | `200 {}` | `400 BAD_REQUEST` (missing, or >72 bytes), `401 UNAUTHENTICATED` (old wrong) |

Password length cap is bcrypt's 72-byte hard limit (`account.MAX_PASSWORD_BYTES`).

`setup` no longer builds the encrypted DB — since 3.2b-1 `create_account` only writes `auth.json`, and the
encrypted `cdr.db` is built lazily by the first `get_db()` (the migration seam, ADR 0002). If that first
build fails during the SETUP audit, `auth.json` already exists so `/api/setup` returns `409` on retry, but
the account is recoverable via `/api/login` (whose audit write builds the DB).

### Datasets & import

| Method | Path | Auth | Body | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/imports` | required | **multipart**: `name` (form) + `file` (.xlsx) | `201 {"dataset_id","imported","skipped","skipped_reasons":[{row,reason}]}` | `400 BAD_REQUEST`/`BAD_FILE`, `400 SCHEMA_MISMATCH` (missing columns), `413 PAYLOAD_TOO_LARGE` (>50 MiB) |
| GET | `/api/datasets` | required | — | `200 [{id,name,filename,imported_at,row_count,skipped_count}]` | — |
| GET | `/api/datasets/<id>/phone-numbers` | required | — | `200 [{phone_number,count}]` | `404 NOT_FOUND` |
| GET | `/api/datasets/<id>/records` | required | query: `offset` (≥0, default 0), `limit` (1–500, default 100), filters (all optional, composable): `phone_number` + `call_type` exact, `area` + `other_party` substring (LIKE wildcards literal); `sort` (`timestamp`\|`duration_seconds`, whitelisted) + `dir` (`asc` default\|`desc`); empty/malformed filter or sort = ignored | `200 {total,offset,limit,phone_number,rows:[...]}` (`total` counts the filtered set) | `404 NOT_FOUND` |
| PATCH | `/api/datasets/<id>` | required | `{name}` (non-empty, trimmed) | `200 {id,name}` | `400 BAD_REQUEST` (blank name), `404 NOT_FOUND` |
| DELETE | `/api/datasets/<id>` | required | — | `200 {}` | `404 NOT_FOUND` |

Import validates every row (`app/datasets/validation.py`): required non-empty `phone_number`/`area`,
ISO-8601 **naive** timestamp (tz-aware rejected), `call_type` in the Phase-1 set, non-negative
`duration_seconds` within int64. Invalid rows are **skipped, not fatal** — reported in `skipped_reasons`.
Deleting a dataset cascades to `cdr_records`, `targets`, and `analysis_results` (FK `ON DELETE CASCADE`).

### Targets

| Method | Path | Auth | Body | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/targets` | required | `{name, dataset_id:int, phone_number:str}` | `201 {id,name,dataset_id,phone_number}` | `400 BAD_REQUEST` (type check), `404 NOT_FOUND` (dataset or phone), `409 CONFLICT` (dup) |
| GET | `/api/targets` | required | — | `200 [{id,name,dataset_id,phone_number,created_at}]` | — |
| PATCH | `/api/targets/<id>` | required | `{name}` (non-empty, trimmed) | `200 {id,name}` | `400 BAD_REQUEST` (blank name), `404 NOT_FOUND` |
| DELETE | `/api/targets/<id>` | required | — | `200 {}` | `404 NOT_FOUND` |

One target per `(dataset_id, phone_number)` — enforced both by a pre-check and the DB `UNIQUE`
constraint (the route maps `IntegrityError → 409`). `GET /api/targets` is **global** (not filtered by
dataset); the UI filters client-side (API-MISMATCH #3 in `main.py`). `PATCH` renames the **label
only** — `phone_number`/`dataset_id` are the identity and stay fixed, so a rename can never collide
with the UNIQUE constraint. Both PATCH renames are surfaced in the SPA via a right-click → Rename
context menu on the dataset and target rows.

### Analysis

| Method | Path | Auth | Query | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/targets/<id>/analyze` | required | `top_n` (default 5, clamped ≥0) | `200 <payload>` (also persisted) | `404 NOT_FOUND` |
| GET | `/api/targets/<id>/result` | required | — | `200 <payload>` | `404 NOT_FOUND` (no target, or no analysis yet) |
| GET | `/api/targets/<id>/frequency` | required | `rank_by` (`area`\|`other_party`\|`call_type`, default `area`), filters: `call_type`, `area`, `date_from`/`date_to` (YYYY-MM-DD), `hour_from`/`hour_to` (0–23, may wrap midnight) | `200 {target,rank_by,total_records,top:[{value,count}]}` | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| POST | `/api/frequency/save` | required | JSON body: `target_id` + the same filter fields as `frequency` | `200 {id, filter_label, …tally}` (persisted) | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| GET | `/api/frequency/saved` | required | — | `200 [{id,target_id,target_name,phone_number,dataset_name,created_at,filter_label,tally}]` | — |
| DELETE | `/api/frequency/saved/<id>` | required | — | `200 {deleted}` | `404 NOT_FOUND` |
| POST | `/api/export/results.xlsx` | required | `target_id` (int, or `all`/omitted for every target) | `200` .xlsx attachment | `404 NOT_FOUND`, `400 BAD_REQUEST` |

`frequency` is the Spreadsheet tab's filtered explorer: a **plain descriptive count** over the
target's filtered records. It deliberately returns no confidence/gates — filters are legitimate
there precisely because a tally has no sample-size gate to distort (unlike `analyze`, which always
runs on the full record set). `frequency/save` is **click-to-save export staging**: it recomputes
the tally server-side from the submitted filters (a client-supplied result payload is never
accepted) and stores it with a human-readable `filter_label`; saved tallies accumulate and are
individually deletable. `export/results.xlsx` writes the **stored** latest answers per target
(never recomputes); un-analyzed targets appear as `not analyzed`. Workbook layout: a styled
`Summary` sheet (one row per target: home/work + confidence) plus `Frequent areas` and
`Frequent contacts` detail sheets — tallies carry **no confidence columns**, same rule as the UI —
plus the always-present `Contact matches` and `Frequency counts` sheets holding the click-to-save
staged items (placeholder row when nothing is saved). The export route lives in `app/reporting/`
(the cross-domain composition surface), and the ?target_id scope applies to the detection sheets
only — the two staged sheets always carry exactly the user's curated saves.

### Contact matcher

| Method | Path | Auth | Body | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/match` | required | `{target_a_id, target_b_id}` (ints, distinct, same dataset) | `200 <match payload>` (stores nothing) | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| POST | `/api/match/save` | required | same as `/api/match` | `200 <match payload>` (recomputed server-side, persisted; replaces a previous save of the same pair — order-normalized, so A↔B = B↔A) | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| GET | `/api/match/saved` | required | — | `200 [{id,dataset_id,dataset_name,created_at,result}]` | — |
| DELETE | `/api/match/saved/<id>` | required | — | `200 {deleted}` | `404 NOT_FOUND` |
| POST | `/api/ledger` | required | `{target_a_id, target_b_id}` | `200 {pair, rows[], row_count, category_counts}` (stores nothing) | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| POST | `/api/ledger/save` | required | same | `200 {id, …ledger}` (recomputed server-side; ledgers **accumulate**, they do not replace) | `404 NOT_FOUND`, `400 BAD_REQUEST` |
| GET | `/api/ledger/saved` | required | — | `200 [{id,dataset_name,created_at,row_count,pair}]` (row counts only — the rows themselves go to the workbook) | — |
| DELETE | `/api/ledger/saved/<id>` | required | — | `200 {deleted}` | `404 NOT_FOUND` |

**Pair record ledger** (`app/matching/ledger.py`, spec `2026-07-13-pair-record-ledger-design.md`) —
a separate feature from the matcher: it LISTS the records, it does not judge them (no strengths, no
confidence anywhere). Each row is one CDR record in one of four categories — `direct` (the pair's own
calls/SMS), `shared_contact` (calls from either side to a contact they both have),
`meet_up_location` / `shared_location` (records in a shared area, split by whether a co-presence event
happened there). Rows carry `who`/`who_phone`, `timestamp`, `call_type`, `duration_seconds`,
`other_party` (+ `other_party_name` and `other_party_is_target` — a shared contact who is themselves a
target is named and flagged), `area`, and `distinctive` (null on direct rows). Common contacts/areas
are **listed and labelled**, never hidden and never called evidence; the label comes from the same
`gates.classify_shared_contacts` / `classify_areas` the verdicts use, so the two cannot disagree.
The UI pages at 50 rows with an Expand control, and filters/sorts **client-side** (the whole ledger is
already in the response, so a round trip would be waste — unlike the records sheet, which pages over a
whole dataset server-side); the workbook's **`Pair records`** sheet is exhaustive.

The matcher is a **gated pair inference** (`app/matching/`): typed findings, each rated
High/Medium/Low by the weakest of the gates applicable to that finding type (`gates.py`;
thresholds are proposals pending domain review). Payload shape:

```jsonc
{
  "pair": {"dataset_id", "target_a": {"id","name","phone_number"}, "target_b": {…}},
  // pair is CANONICAL (sorted by phone number): A-vs-B and B-vs-A return
  // byte-identical results regardless of which box each target was put in
  "computed_at": "<iso>",
  "dataset_context": {                    // adaptive gates (spec 2026-07-13/-07-14)
    "mode": "strangers" | "close-knit",   // which mutual-contact rule-set applied
    "classification": "High" | "Medium" | "Low" | "Near tie",  // how decisively
    "avg_shared_contacts_per_pair": 0.55, "boundary": 2.0, "subscribers": 40,
    "mode_note": "<optional>"             // present only when the mega-popular
                                          // many/few cutoff is near (mode could flip)
  },
  "findings": [{
    "type": "direct_contact" | "mutual_contacts" | "co_presence",
    "label": "Direct contact" | "Mutual relationship" | "Meeting up",
    "strength": "High" | "Medium" | "Low",
    "bound_by": ["<gate name>", …],      // which gate(s) sit at the min()
    "notes": ["sample is just short of High: 49 vs 50", …],  // cliff disclosure
    "headline": "<one-line summary>",
    "evidence": {…}                       // per-type: direct counts / shared_contacts / events (+gates)
  }],
  "caveats": ["<honesty notes: tiny window overlap, zero records, tiny population>"],
  "details": {"windows": {"a","b","overlap_ratio"}, "shared_areas_no_time_overlap": […]},
  "no_link": false                        // true when findings is empty
}
```

Gate design: *direct contact* is positive evidence rated by deduplicated physical interaction
volume (mirrored incoming/outgoing legs count once, and doubt gates never drag it down); *mutual
relationship* = min(contact-record sample N both sides, overlap share, distinctiveness, window
overlap); *meeting up* = min(located-record sample, event count, location distinctiveness, window
overlap). Same-area hits within 60 minutes are grouped into temporal sessions per area; each event
shows the closest actual matched time pair. Shared areas **without** time overlap remain a detail.

**Distinctiveness is dataset-adaptive** (specs `2026-07-13-adaptive-matcher-gates.md` +
`2026-07-14-conditional-hub-counting-design.md`): the dataset's interconnectedness (average shared
contacts per subscriber pair, boundary 2.0) picks the rule-set. Mega-popular contacts (spread ≥ 50%
of subscribers) are counted **conditionally** — included as group fabric when many of them exist
(≥ max(2, 0.15·n)), excluded as lone services when few — so a hub-and-spoke family reads close-knit
while a stray service line can't flip a strangers dataset. The classification is disclosed with its
own confidence tier ("Near tie" = right on the boundary; ratings may flip between imports), and
`dataset_context.mode_note` fires when the many/few count itself sits near its cutoff. In
**strangers** mode, contacts/areas that ≥ 20% of the other subscribers also have are discounted
(pizza-place / busy-tower), with a
floor: fewer than `COMMON_MIN_USERS=3` other subscribers never brand anything common, and a
population under 10 other subscribers adds a caveat and caps indirect findings at Medium. In
**close-knit** mode, hub-only overlap is suppressed: at least one contact rarer than the dataset's
true median shared-contact spread is required. One rare contact rates Medium and ≥ 2 rate High
before the other gates are applied. Area commonality stays absolute in both modes. Every threshold
is a PROPOSAL flagged in `gates.py` for domain review.

`analyze` runs the five frozen Phase-1 detectors via the `app/analysis/bridge.py` seam and stores the
result JSON. Payload shape:

```jsonc
{
  "target": {"id", "name", "phone_number"},
  "analyzed_at": "<iso>",
  "home":  <DetectionResult>,          // area, confidence, confidence_label, near_tie,
  "work":  <DetectionResult>,          //   alternatives[], supporting_records, total_window_records,
  "frequent_areas": [{"area","count","share"}],   //   share, closeness, density, gates
  "frequent_areas_confidence": <DetectionResult>,
  "frequent_contacts": [{"number","total","call_out","call_in","sms_out","sms_in"}]
}
```

## Audit side effects

Every state-changing endpoint writes an `audit_log` row inside the same transaction it commits
(`app/audit/log.py`): `SETUP, LOGIN_SUCCESS, LOGOUT, CHANGE_PASSWORD, IMPORT, DATASET_DELETE,
DATASET_RENAME, TARGET_CREATE, TARGET_DELETE, TARGET_RENAME, ANALYSIS, EXPORT, PAIR_MATCH_SAVE,
PAIR_MATCH_DELETE, TALLY_SAVE, TALLY_DELETE`. Running a match or a tally is a read and is **not** audited (like `frequency`);
changing what the export will contain is a mutation and is. `EXPORT` changes no app state, but detection
answers leaving the encrypted store is exactly what the trail is for; it is a **POST** (not a GET)
precisely so the audited action can't be replayed by a browser/webview HEAD, prefetch, or reload.
Failed logins can't reach the encrypted DB (no key), so they
append to the plaintext `login_failures.log` sidecar (`LOGIN_FAIL`) — best-effort, **not** tamper-evident.
