# Phase 3 · Increment 3.2a — Identity-accessor De-globalization — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the operator's *identity* out of process-global `app.config["USERNAME"]` into a per-session context (`app/api/identity.py`, SUPPORT, data-free) so a single server can hold more than one unlocked operator at once — swapping only the accessor and its two writers, leaving behavior frozen for the single-account desktop app.

**Architecture:** Add one leaf SUPPORT module, `app/api/identity.py`, that reads/writes the operator username in Flask's signed `session` cookie. `app.api.guards.current_username()` swaps its body to delegate to it (ADR 0001 invariant 6 — one accessor body changes, not the ~7 call sites). `app/auth/routes.py` writes it at login/setup (`_unlock`) and clears it at logout/failed-auth (`_lock`, via the existing `session.clear()`). The `USERNAME` default is removed from `app/__init__.py`. **`DB_KEY` is deliberately NOT touched** — under the chosen server-holds-the-master-key model it stays process-global (reinterpreted as the *server* master key in 3.2b), so there is no per-session DB key to eliminate here. DB-backed role/identity accessors are an `authz`-tier concern that arrives with multi-account (3.2b/3.3); a SUPPORT module never reads the DB.

**Tech Stack:** Python 3.11, Flask (`session` cookie + `g`/app-context), pytest, `ast` (architecture guard), import-linter (CI boundary gate). No new dependencies.

## Global Constraints

- **Phase 1 (`phase1_cdr/`) is FROZEN** — do not touch. Verify `git diff --stat main -- phase1_cdr/` is empty before every commit.
- **Synthetic-data portfolio app** — no real/live-data or surveillance features.
- **Layer rule (CI-enforced):** APPLICATION → DOMAIN → AUDIT → SUPPORT → INFRA. `app/api/identity.py` is a **leaf SUPPORT** module: it may import `flask` only and **must not** import any `app.*` module, read the DB, or issue SQL. `app/api/guards.py` (SUPPORT) may import it (same tier, downward). `app/auth/routes.py` (APPLICATION) may write it (higher calls lower).
- **Invariant 6 (single accessor seam):** identity is read only through `app.api.guards.current_username()`; call sites never read `config["USERNAME"]` directly. This increment swaps that one body — the read-only consumers (`datasets/targets/analysis/auth` routes) get **zero edits**. If any consumer needs editing, the seam leaked; fix the accessor, not the call site.
- **`DB_KEY` stays process-global** in `app.config` (server master key). Do **not** move it into the session, and do **not** remove its `app/__init__.py` default. Only *identity* de-globalizes.
- **Behavior-frozen:** for the single-account, single-client desktop app there is exactly one session, so moving identity from a process global to that session's cookie changes nothing observable. The full suite is the regression net.

- [ ] **Step 3: Create `app/api/identity.py`**

```python
"""Per-session identity context (SUPPORT layer).

Holds *who* the operator is on THIS request's session, in the signed session
cookie -- today just the username. Phase 3 multi-account (3.2b) adds `user_id`
here. This module is deliberately **data-free**: it never opens or reads the
database. DB-backed identity/role accessors (role + `disabled` resolved from the
`users` row) are an `authz`-tier concern that arrives with multi-account -- a
SUPPORT module reading the DB would invert the layer rule (ADR 0001; ADR 0003).

Keeping identity per-session here (not in process-global `app.config`) is what
lets one server hold more than one unlocked operator at once. `current_username()`
in app.api.guards delegates to this module, so call sites never change (ADR 0001
invariant 6). The DB key stays process-global (the server master key); only
identity de-globalizes.
"""

from __future__ import annotations

from flask import session

_USERNAME_KEY = "username"


def set_identity(username: str) -> None:
    """Bind the current session to `username` (auth routes call this at login/setup)."""
    session[_USERNAME_KEY] = username


def current_username() -> str | None:
    """The username bound to the current request's session, or None."""
    return session.get(_USERNAME_KEY)


def clear_identity() -> None:
    """Remove the identity from this session (logout also calls session.clear())."""
    session.pop(_USERNAME_KEY, None)
```

```python
def test_identity_context_is_data_free():
    """The SUPPORT per-session identity context (app/api/identity.py) must never
    touch the DB: no SQL execution, and no app.* import at all (it is a leaf that
    reads only flask.session). DB-backed identity/role accessors are authz-tier
    (arrive with multi-account), not here -- a SUPPORT DB read inverts the layer
    rule (ADR 0001; ADR 0003; spec Codex #3)."""
    tree = ast.parse(_IDENTITY.read_text(encoding="utf-8"))

    sql = [n.lineno for n in ast.walk(tree)
           if isinstance(n, ast.Call) and isinstance(n.func, ast.Attribute)
           and n.func.attr in _SQL_CALLS]
    assert not sql, f"identity.py must issue no SQL: lines {sql}"

    app_imports = []
    for node in ast.walk(tree):
        if isinstance(node, ast.ImportFrom) and (node.module or "").split(".")[0] == "app":
            app_imports.append((node.lineno, node.module))
        elif isinstance(node, ast.Import):
            app_imports += [(node.lineno, n.name) for n in node.names
                            if n.name.split(".")[0] == "app"]
    assert not app_imports, f"identity.py must not import app.* (data-free leaf): {app_imports}"
```

```markdown
# ADR 0003 — Server master key and per-session identity

- **Status:** accepted
- **Date:** 2026-07-05
- **Deciders:** Nadim (merges); proposed by Claude, reviewed by Codex

> **Scope note:** this ADR records the Phase 3 auth/key trust model and is built
> incrementally. **Part 1 (increment 3.2a, this record) covers identity
> de-globalization.** **Part 2 (increment 3.2b)** — the server master key set at a
> manual bootstrap passphrase and the multi-account `users` table replacing
> `auth.json` — will be appended as a dated section to *this same ADR*, not minted
> under a new number (mirroring ADR 0002's in-place "Activation" note).

## Context

Today auth state is two process-global slots in `app.config`: `DB_KEY` (the raw
SQLCipher key) and `USERNAME` (the logged-in operator), both set at login and
cleared at logout. Phase 3 turns the app into a LAN multi-user server that can
hold **more than one unlocked operator at once** — so identity cannot be a single
process global shared across all connected clients. The de-globalization surface
was inventoried pre-Phase-3 (`docs/phase3-surface.md`) behind a single accessor
seam (`api.guards.current_username()`, ADR 0001 invariant 6) precisely so this
move changes one function body, not every call site.

The design review (spec §4.2, Codex #2/#3) corrected an early premise: under the
chosen **server-holds-the-master-key** model, only *identity* de-globalizes.
`DB_KEY` stays process-global because there is exactly **one** master key for the
whole server; there is no per-session DB key to eliminate.

## Decision

**Part 1 (3.2a): identity is a per-session, data-free SUPPORT context.**

- Add `app/api/identity.py` (SUPPORT). It stores the operator identity — the
  username today, `user_id` in 3.2b — in Flask's **signed `session` cookie**
  (already per-client). It imports `flask` only.
- **Rule:** `app/api/identity.py` is a **leaf** — it must never import an `app.*`
  module, open the database, or issue SQL. A SUPPORT module that read the DB would
  invert the layer rule. DB-backed identity/role accessors
  (`authz.current_username()` / `authz.current_role()`, resolving `role`/`disabled`
  from the `users` row) are an **`authz`-tier** concern and arrive with
  multi-account (3.2b/3.3), not here. Enforced by `tests/architecture/`
  (`test_identity_context_is_data_free`) + the import-linter layers contract.
- `api.guards.current_username()` swaps its body to delegate to
  `identity.current_username()`. Read-only call sites are untouched (invariant 6).
- `auth/routes.py` (APPLICATION) writes the identity at login/setup and clears it
  at logout/failed-auth. `DB_KEY` remains a process-global `app.config` slot and is
  **not** moved to the session.

## Consequences

- **Easier/safer:** identity is now per-client; the server is structurally ready to
  hold several unlocked operators once multi-account lands. The move is
  behavior-frozen for the single-account desktop app (one session).
- **Giving up:** nothing observable today. Identity now rides the session cookie
  (already signed, `HttpOnly`, `SameSite=Strict`), so it is bounded by the cookie's
  integrity — acceptable, and the same store `session["authenticated"]` already uses.
- **Defers to 3.2b (part 2):** the server master key set at a manual bootstrap
  passphrase; the `users` table (bcrypt hashes, roles, `disabled`) replacing
  `auth.json`; `session` carrying `user_id` (not a bare username) with live
  role/`disabled` read per request via `authz`. Trigger: increment 3.2b. Those
  append to this ADR.

## Alternatives considered

- **De-globalize `DB_KEY` into per-session context too** (the original
  `phase3-surface.md` premise) — rejected: under server-holds-the-master-key there
  is one key for the whole server; a per-session key would mean caching a
  password-derived key server-side (new infra) or putting it in a
  signed-not-encrypted cookie (unsafe). `DB_KEY` is reinterpreted as the server key,
  not eliminated. (spec §4.2, Codex #2)
- **Put the identity context in `auth/` DOMAIN** (an early `auth/session.py` idea) —
  rejected: `api.guards` (SUPPORT) reads it, so `guards → auth` would invert the
  layer rule. It belongs in SUPPORT (`app/api/identity.py`). (spec §4.2, Codex #3)
- **Store live role/username in this SUPPORT context** — rejected: those need a DB
  read and must be `authz`-tier; SUPPORT stays data-free. (spec §5, Codex #4)
```
