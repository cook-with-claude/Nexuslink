# Phase 1 — CDR Pattern Detection (Algorithm Validation)

[![CI](https://github.com/cook-with-claude/La-Passion/actions/workflows/ci.yml/badge.svg)](https://github.com/cook-with-claude/La-Passion/actions/workflows/ci.yml)

Phase 1 of a CS portfolio project. The goal is narrow and deliberate: **prove the
pattern-detection algorithm is correct against synthetic data with a known ground
truth**, before any UI, server, or account work in later phases.

## Important: synthetic data only

Every CDR row in this project is **synthetic**, generated by code with a fixed random
seed. No real telecom data and no LLM is ever used to produce rows. None of this code
touches the network, a UI, or an account system — that is by design, not an omission.
`dev_fixtures.py` is a throwaway dev generator and is meant to be deleted once the
team's real (still synthetic) generator exists.

## What it does

- **`loader.py`** — reads a `.csv` / `.xlsx` / `.xls` CDR file into a validated
  DataFrame (9-column schema, see below), dropping rows with bad timestamps or invalid
  `call_type` and warning about them.
- **`detection.py`** — pure functions that infer a user's likely **home** area
  (overnight), **work** area (weekday daytime), most **frequent** areas, and most
  **frequent contacts**. Home/work/frequent-areas each carry a confidence label
  (`High` / `Medium` / `Low` / `Insufficient data`) produced by the four-gate model
  described below. A near-tie result is tagged (`Low: near tie`) and lists the close
  areas as `alternatives`.
- **`dev_fixtures.py`** — deterministically builds `sample_data.csv` and an
  *independently computed* `ground_truth.json` for five test users. Each user also
  has a fixed **contact pool**; counterparties are drawn with a separate RNG so the
  home/work/confidence data stays identical to the pre-contacts fixtures.
- **`validate.py` / `main.py`** — run the detectors against the ground truth and print
  two pass/fail tables (locations, then ranked contacts).

## CDR schema (9 columns)

Each row is one telecommunication event for the **subject** (`phone_number`), and
also records the **counterparty** it involved:

| Column | Meaning |
|---|---|
| `phone_number` | the subject whose CDR this is |
| `imei` | the subject's device |
| `area` | the subject's location at the time of the event |
| `timestamp` | event time |
| `call_type` | `1` call out · `2` call in · `11` SMS out · `22` SMS in |
| `duration_seconds` | call duration |
| `other_party` | the number the subject communicated with |
| `other_imei` | the counterparty's device |
| `other_area` | the counterparty's location |

**Every query is single-subject** — a detector looks only at the subject's own
rows. The counterparty columns exist for realism/consistency; only `other_party`
is read by any query (the contacts ranking). `other_imei` / `other_area` are
carried but not yet used.

## The frequency query

`detect_frequent_areas` and `detect_frequent_contacts` together answer "what does
this subject do most":

- **Frequent locations** — the subject's top-5 areas, each with its **percentage**
  (share of the subject's calls). Uses the Share gate alone for the lead area's
  confidence (habits, not a single inferred location).
- **Frequent contacts** — the subject's top-5 counterparty numbers, ranked by total
  telecommunications, each broken down **4-way by type** (call out / call in /
  SMS out / SMS in). A raw frequency ranking — no confidence gates apply.

Both default to top-5 via a `top_n` parameter, so a later UI can request more.

## Confidence model (four-gate, weakest-link)

The winner is always the area with the most calls in the window; confidence only
says **how much to trust it**. Four independent gates are each scored
`High` / `Medium` / `Low`, and the final confidence is the **lowest** of the four —
a strong gate never rescues a weak one:

| Gate | Question | Measure |
|---|---|---|
| **N** | Enough calls at all? | absolute count in the window |
| **Share** | Does the winner dominate? | winner / total calls |
| **Closeness** | Is it a near-tie? | runner-up / winner (inverted) |
| **Density** | Enough coverage for how long we've watched? | distinct active days ÷ days observed |

**N and Density are complementary** — N is an absolute floor (a tiny sample can
never score High, even at 100% coverage), while Density makes the same volume
question *relative* to the observation span: a handful of records over a week is
decent coverage; the same handful over three years is not. Short span → N governs;
long span → Density governs.

When Closeness flags a near-tie, the result is tagged `Low: near tie` and the close
areas (those within ~70% of the winner) are surfaced as `alternatives` rather than
silently dropped. **Frequent** areas are about habits, not a single inferred
location, so they use the Share gate alone (no closeness / near-tie).

> **Thresholds:** `N_HIGH=50` / `N_MEDIUM=15` and `DENSITY_HIGH=0.40` /
> `DENSITY_MEDIUM=0.15` in `detection.py` are calibrated to the realistic fixtures
> (per-user volumes of 500–5000 calls over spans of weeks to a year). Share and
> Closeness are scale-invariant ratios and need no tuning. Re-tune `N_*` / `DENSITY_*`
> again if the real generator changes the volume or span distribution.

## Usage

Regenerate the fixtures (deterministic — identical output every run):

```bash
python dev_fixtures.py
```

Run the validation harness (prints a table, exits non-zero if anything fails):

```bash
python main.py sample_data.csv ground_truth.json
```

Run the unit tests:

```bash
pytest tests/
```

## The five test users

Each carries a realistic volume (500–5000 calls) over a different observation span,
so every gate gets exercised. C is the deliberate small-sample exception.

| User | Pattern | Span / volume | Home expectation | Work expectation |
|---|---|---|---|---|
| A | Consistent commuter | ~365d, ~1060 | exact area, `High` | exact area, `High` |
| B | Noisy, real plurality | ~180d, ~990 | exact area, ≤ `Medium`, alt `Hamra` | exact area, ≤ `Medium` |
| C | Sparse floor case (no in-window data) | ~21d, ~40 | none, `Insufficient data` | none, `Insufficient data` |
| D | Adversarial / no stable pattern | ~180d, ~1010 | exact area, ≤ `Medium`, alt `Achrafieh` | exact area, ≤ `Low`, alts `Mazraa`,`Verdun` |
| E | Long span, sparse window | ~365d, ~600 | exact area, **exactly** `Low` (Density-bound) | none, `Insufficient data` |

User **E** is the dedicated **Density** case: ~30 unanimous overnight calls scattered
across a full year. N (Medium), Share (High) and Closeness (High) all look strong, but
~30 active nights over 365 days is thin coverage, so **Density alone caps the result to
`Low`**. Its home confidence is pinned *exactly* to `Low` (not a ceiling), and the
fixture should still be gate-traced during review because confidence alone cannot
encode which gate produced the cap.

User D is the real stress test. The detector still **names** the plurality area (that
is what it returns), but it must **resist** calling a near-coin-flip or scattered
pattern "High confidence" — instead it caps the confidence and **flags the near-tie**,
listing the close areas as `alternatives`. (Earlier the ground truth claimed D returned
*no* area; that was never true — the detector always returned the plurality, so the
expectation now matches reality and the area check is actually enforced.)

## Why ground truth is computed independently

`ground_truth.json` is built inside `dev_fixtures.py` by tallying counts in the known
time windows with plain `groupby` — it never imports `detection.py`. If the ground
truth were produced by the function under test, the validation would prove nothing.
