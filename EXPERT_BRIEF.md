# CDR Location-Inference — Technical Brief for Expert Review

**Purpose of this document:** explain, to someone who knows CDRs and telecom well,
exactly what we have built so far, the logic and assumptions behind it, and where we
most want your judgement. We are **not** asking you to read code — this describes the
*method*. Push back hard anywhere the domain logic is naive.

---

## 1. What this is (and what it deliberately is not)

We are building a system that infers a subscriber's likely **home area**, **work
area**, and **frequently-visited areas** from their CDRs.

What we have completed is **Phase 1: algorithm validation only.** The single goal of
this phase was to prove the inference logic and — more importantly — its **confidence
model** are correct against a *known answer*, before any product, UI, or real-data
pipeline is built on top.

Two things to be clear about up front, because they shape everything below:

- **All data is currently synthetic.** Every CDR is generated by our own code with a
  fixed random seed. There is no real network data, no roaming, no live feed. This is
  intentional — we wanted a ground truth we control so we could *prove* the algorithm,
  not guess at it.
- **The synthetic generator is a throwaway.** It exists only to exercise the algorithm.
  The real (still synthetic-at-first, then real) data generator is future work, and it
  must emit the **same 9-column schema** below. **This is the seam where your input
  matters most** — what the real data actually looks like will decide whether our
  assumptions hold.

---

## 2. The data model (the 9-column CDR schema)

Each record is one row with these fields. The first six are the original schema;
the last three were added to support a **frequent-contacts** ranking (see §3):

| Column | Type | Notes |
|---|---|---|
| `phone_number` | string | subscriber identifier; kept as string so leading zeros survive |
| `imei` | string | handset identifier; **currently carried but not used in inference** |
| `area` | string | a **location label** — see the big caveat below |
| `timestamp` | datetime | when the event occurred |
| `call_type` | integer code | one of `{1, 2, 11, 22}`; not used in *location* inference, but the frequent-contacts ranking splits a contact's events 4-way by this code |
| `duration_seconds` | integer | **carried but not used in inference** |
| `other_party` | string | the counterparty number; **read only by the frequent-contacts ranking** — the one query that looks beyond the subject's own rows |
| `other_imei` | string | counterparty handset; **carried but read by no query yet** |
| `other_area` | string | counterparty location; **carried but read by no query yet** |

The loader validates the schema, drops rows with unparseable timestamps or a
`call_type` outside the allowed set (warning on each), and otherwise does no cleaning.

**Two things we specifically want your view on here:**

1. **`area` is an opaque label in our current data.** In the synthetic set it is just a
   neighbourhood name (Hamra, Achrafieh, Downtown, Verdun, Mazraa). It carries **no cell
   geometry, no Cell-ID / LAC / TAC, no overlap, no handover modelling, no signal
   strength.** Every record cleanly "is" in exactly one area. We know real serving-cell
   data is nothing like this clean. **How `area` should be derived from real CDRs —
   raw Cell-ID, a clustered cell group, or a geocoded zone — is an open design question
   we'd value your steer on**, because every confidence number we compute is only as
   meaningful as that upstream step.
2. **We currently ignore `call_type`, `duration_seconds`, and `imei` entirely** in the
   inference. Inference uses only `phone_number`, `area`, and `timestamp`. Question for
   you: are the `call_type` codes `{1, 2, 11, 22}` a sensible set (we assumed something
   like MO/MT voice and MO/MT SMS), and should call direction, event type, or duration
   actually inform a location guess? (e.g. should a 10-second event weigh the same as a
   20-minute call as evidence of *being somewhere*?)

## 3. What we infer, and the core heuristic

Four outputs, per subscriber:

- **Home area** — inferred from **overnight events only: hour ∈ [00:00, 06:00), any day
  of the week.** The assumption: wherever the phone is at 3 a.m. is home.
- **Work area** — inferred from **weekday daytime events only: hour ∈ [09:00, 18:00),
  Monday–Friday.** Weekends explicitly excluded.
- **Frequent areas** — top areas across **all** events, no time filtering, each shown
  with its **% share**. These are "habitual hangouts", not a single inferred anchor.
- **Frequent contacts** — the top counterparty numbers (`other_party`) by event
  volume, each split 4-way by `call_type` (call-out / call-in / SMS-out / SMS-in).
  This is **descriptive analytics, not a location inference**, so it carries no
  confidence gates — it is a raw frequency ranking only.

**The winner is always simply the plurality** — the area with the most events inside the
relevant time window. There is no clever math in *picking* the answer. A deterministic
tie-break (count desc → earliest timestamp → area name) keeps it reproducible.

We are aware these windows are heuristics that break for night-shift workers, shift
healthcare/hospitality staff, cross-timezone subscribers, etc. **We'd welcome your sense
of whether these windows match what you've seen work on real CDRs**, and whether a
sanity cross-check (e.g. "does the home anchor also dominate weekends?") is worth adding.

## 4. The confidence model — this is the heart of it

Naming the most-frequent area is the easy part. The real work — and what Phase 1 is
about — is **quantifying how much to trust that answer.** A plurality can be meaningless
for several independent reasons, so we score it through **four independent "gates",**
each rated **High / Medium / Low**:

| Gate | Question it answers | Measure |
|---|---|---|
| **N** | Is there enough data at all? | absolute event count in the window |
| **Share** | Does the winner actually dominate? | winner count ÷ total window count |
| **Closeness** | Was it a blowout or a photo-finish? | runner-up ÷ winner (inverted) |
| **Density** | Is the evidence spread out, or a fluke of timing? | distinct active days in window ÷ total days observed |

### 4.1 The aggregation rule: weakest link wins

**Final confidence = the *lowest* of the four gates.** Not the average, not the best.

This is the single most important design decision. It is deliberately pessimistic: if
three gates say High and one says Low, the answer is **Low**. A strong signal is never
allowed to rescue a fatal weakness. The reasoning: in location inference *any single*
disqualifying flaw (e.g. only 6 events) invalidates the guess, and an averaging model
would let the good-looking dimensions paper over that flaw.

### 4.2 Why N and Density both exist

They sound redundant but are not:

- **N is an absolute floor** — below a minimum event count you can't be confident,
  regardless of how clean the pattern looks.
- **Density makes the same volume question *relative to the observation span*** — 30
  overnight events is strong over one week, but thin if scattered across a full year.

So they hand off: over a **short** span, N governs; over a **long** span, Density
governs and catches the subscriber who *looks* consistent but is actually sparse across
years of history. **Density counts distinct *active days*, not raw event count** — a
deliberate choice so that one unusually chatty night can't masquerade as many nights of
evidence, and so Density isn't just a restatement of N.

### 4.3 Near-ties and alternatives

When the runner-up area is close to the winner (runner-up > ~70% of the winner), we do
**not** silently pick one. We tag the result `Low: near tie` and **list the close areas
as `alternatives`.** This is intentional — real subscribers genuinely have two anchors
(dual residence, a partner's place, split custody), and collapsing that to one confident
answer would be *wrong*, not merely imprecise.

**Frequent areas use the Share gate only** — no closeness / near-tie logic — because
habitual areas aren't a single location to pin down.

### 4.4 The thresholds (and the honest caveat)

Current cut points:

- **N:** High ≥ 50 events, Medium ≥ 15, else Low.
- **Share:** High ≥ 0.40, Medium ≥ 0.10, else Low.
- **Closeness** (runner-up/winner): High ≤ 0.30, Medium ≤ 0.70, else Low = near-tie.
- **Density:** High ≥ 0.40, Medium ≥ 0.15, else Low.

**Share and Closeness are scale-free ratios** and need no tuning. **N and Density are
calibrated to our synthetic volumes** (per-subscriber 500–5000 total events over spans
of weeks to a year) and we fully expect they will need re-derivation against real
per-subscriber event-rate and observation-span distributions. **This is a place we'd
specifically like your read** — what do realistic per-subscriber CDR volumes and history
lengths actually look like, and are these floors anywhere near right?

## 5. How we proved it works (validation methodology)

We built **five synthetic subscriber archetypes**, each engineered to stress a different
gate, and gave each a *different observation span* so the relative Density gate is
actually exercised:

| User | Archetype | Span / volume | Expected result |
|---|---|---|---|
| **A** | Consistent commuter | ~365 d, ~1060 events | Home & work **High** — the clean case |
| **B** | Noisy, genuine near-tie | ~180 d, ~990 | Home capped ≤ **Medium**, alternative flagged |
| **C** | Sparse, no in-window data | ~21 d, ~40 | **Insufficient data** for home & work |
| **D** | Adversarial, no stable pattern | ~180 d, ~1010 | Names the plurality but must **refuse High**; flags near-tie + alternatives |
| **E** | Long span, sparse window | ~365 d, ~600 | Home pinned **exactly Low** — Density is the *sole* gate that caps it |

User **E** is the important one: ~30 perfectly unanimous overnight events scattered
across a whole year. N, Share, and Closeness all read strong; only Density catches that
~30 active nights over 365 days is thin coverage. E exists to prove the Density gate
actually does its job and isn't dead weight.

**The critical methodological point:** the "right answers" (`ground_truth.json`) are
computed by a **completely separate tally** that never touches the inference code — it
just groups and counts events in the known time windows. If the inference code were
allowed to generate its own answer key, passing would prove nothing. By keeping them
independent, the pass means something. **Current result: 34 of 34 checks pass**, plus
18 unit tests, run automatically on every change.

## 6. Known limitations we already see (and want your help sharpening)

We are not claiming this is production-ready. The open questions we're most aware of:

1. **`area` quality is everything and is currently idealised.** Real serving-cell data
   has overlapping footprints, the phone attaches to the best-radio cell rather than the
   nearest, cell sizes vary enormously (dense downtown vs. sparse suburb), and there are
   mid-call handovers. Our clean one-area-per-event model hides all of this. In
   particular we suspect the **Share** gate is implicitly biased: a subscriber in a
   dense-cell area will look more "fragmented" than a suburban one for reasons unrelated
   to their actual mobility.
2. **CDRs are event-triggered, not a location feed.** We only observe the subscriber
   when they generate a billable event, which biases toward heavy communicators and
   toward places people use their phones. Density partly compensates, but the underlying
   sampling bias is structural.
3. **Share and Closeness partially overlap.** A dominant winner mechanically produces a
   small runner-up ratio, so the weakest-link `min()` slightly double-counts
   "dominance". We've considered replacing Closeness with a concentration/entropy measure
   over the whole area distribution rather than just #1-vs-#2.
4. **`min()` is blind to *how many* gates are weak.** One Medium gate and four Medium
   gates both report "Medium", though the second subscriber is clearly shakier.
5. **Time-window heuristics break for non-standard schedules** (night shift, etc.) and
   the model can't currently tell when it's been fooled.
6. **Thresholds are calibrated to synthetic volumes** and will need re-derivation on
   real distributions (see §4.4).

## 7. The specific questions we'd love your evaluation on

1. How should **`area`** be derived from real CDRs — raw Cell-ID, clustered cell groups,
   or geocoded zones — and what does that do to the confidence logic?
2. Are the **home (00–06) and work (09–18 weekday) windows** realistic, and is a
   weekend/anchor cross-check worth adding?
3. Should **`call_type` / direction / `duration`** inform the location guess at all, and
   are `{1, 2, 11, 22}` a sane code set?
4. What do **realistic per-subscriber event volumes and history spans** look like, so we
   can re-calibrate the **N** and **Density** thresholds against reality?
5. Is the **weakest-link `min()`** the right aggregation, or have you seen better-behaved
   confidence schemes for this kind of inference?
6. Anything in the four-gate decomposition that's redundant, missing, or naive from a
   real-CDR standpoint.

Thank you — your read on §2, §4, and §6 in particular will directly shape what we build
next.
